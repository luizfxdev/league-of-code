## 1. Visão geral: por que Java 17

Java 17 **não é uma versão incremental** de Java 8. São nove anos de evolução, com mudanças na linguagem, na JVM, nas APIs e na política de releases. O salto é grande o bastante para exigir decisões conscientes sobre **o que adotar** e **o que ignorar**.

### Quatro dimensões de mudança

| Dimensão | O que mudou | Exemplos |
|---|---|---|
| Linguagem (sintaxe e expressividade) | Menos código para dizer a mesma coisa | `record`, `sealed`, pattern matching, `switch` expression, `var`, text blocks |
| JVM e performance | Ganhos transparentes, sem refatorar | G1GC como padrão, ZGC disponível, startup e footprint melhores |
| APIs | Novas coleções imutáveis e métodos utilitários | `List.of`, `String.strip/lines/repeat/isBlank`, `Optional` melhorado, `java.time` |
| Remoções e compatibilidade | Coisas que **quebram** ao subir de versão | JPMS, encapsulamento forte (`--illegal-access` removido), `java.xml.ws`, Nashorn, Applet |

### Analogia logística

Migrar de Java 8 para 17 é como **trocar a frota de uma transportadora**:

- Os caminhões novos (linguagem) carregam mais com menos viagens.
- O motor novo (JVM) rende melhor sem você mexer em nada.
- Mas algumas **rotas antigas foram fechadas** (APIs removidas) e você precisa descobrir isso *antes* de sair com a carga.

> **Princípio central: evolução gradual.** Migrar o compilador para 17 é a primeira etapa. Adotar as novas features é a etapa seguinte, e deve ser guiada por **ganho real**, não por novidade.

### LTS: qual versão importa

| Versão LTS | Ano | Observação |
|---|---|---|
| Java 8 | 2014 | Legado ainda muito presente |
| Java 11 | 2018 | Ponte intermediária |
| **Java 17** | **2021** | **Alvo deste guia** |

LTS (*Long Term Support*) é a versão com suporte estendido. Em produção, a regra prática é migrar de LTS para LTS.

## 2. Linha do tempo (Java 9 a 17)

| Versão | Recurso relevante | Por que importa em legado |
|---|---|---|
| Java 9 (2017) | JPMS, `private` em interfaces, `Stream.takeWhile/dropWhile`, `Optional.ifPresentOrElse` | Modularização e streams mais expressivas; JPMS pode quebrar dependências |
| Java 10 (2018) | `var` (inferência local), `List/Set/Map.copyOf` | Menos verbosidade em variáveis locais; `copyOf` é a forma correta de cópia imutável |
| **Java 11 (LTS, 2018)** | `String.strip/lines/isBlank/repeat`, `Files.readString/writeString`, `HttpClient`, remoção de EE/CORBA | APIs de `String` mais seguras (Unicode-aware); remova dependências que saíram do JDK |
| Java 12-13 (2019) | `switch` expression (preview), text blocks (preview) | Ainda preview: familiarize-se, mas não use em produção |
| Java 14 (2020) | Records (preview), pattern matching `instanceof` (preview), NPE com detalhe | NPE melhorado é ganho com zero esforço |
| Java 15-16 (2020-21) | Text blocks estável, records estável, pattern matching `instanceof` estável | **Marco de adoção segura**: features prontas para produção |
| **Java 17 (LTS, 2021)** | Sealed classes, `switch` com pattern (preview), Security Manager *deprecated for removal*, encapsulamento forte | LTS alvo; encapsulamento forte pode quebrar frameworks antigos |

> `switch` expression ficou estável no Java 14.

## 3. Tabela comparativa Java 8 vs Java 17

| Tema | Java 8 | Java 17 | Quando aplicar em legado |
|---|---|---|---|
| Coleções imutáveis | `Collections.unmodifiableList(Arrays.asList(...))` | `List.of(...)`, `Set.of(...)`, `Map.of(...)` | Sempre que a coleção não muda |
| Strings multilinha | Concatenação com `+ "\n"` ou `StringBuilder` | Text blocks (`"""`) | SQL, templates, JSON hardcoded |
| Dados imutáveis (DTO) | Classe com campos, getters, `equals`, `hashCode`, `toString` manuais | `record` | DTOs, respostas de API, objetos de valor |
| Pattern matching | `instanceof` + cast manual | `if (x instanceof String s)` | Onde há `instanceof` seguido de cast |
| `switch` | Statement com `break` | Expression com `->` e `yield` | Quando o `switch` está em atribuição ou `return` |
| Variáveis locais | Tipo explícito sempre | `var` | Quando o tipo é óbvio pelo lado direito |
| Ausência de valor | `null` | `Optional.ofNullable`, `ifPresentOrElse`, `or()` | Retorno de método, nunca campo |
| Espaços em `String` | `trim()` (só ≤ U+0020) | `strip()` (Unicode-aware) | Sempre substituir |
| Data e hora | `Date`, `Calendar` (mutáveis, não thread-safe) | `java.time` | Migrar ao tocar no código |
| `NullPointerException` | Mensagem genérica | Mensagem diz **qual** variável era `null` | Automático |
| Garbage Collector | Parallel GC padrão | G1GC padrão; ZGC disponível | Automático |
| Encapsulamento | Reflection livre nos internals do JDK | `--illegal-access` removido; módulos encapsulados | Verificar dependências antes de migrar |
| APIs removidas | JAX-WS, CORBA, Nashorn, Applet | Removidas ou movidas para Jakarta EE | Identificar e substituir antes |
| Hierarquia de tipos | Qualquer classe pode estender | `sealed` + `permits` | Hierarquias de domínio fechadas |
| Segurança | Security Manager | Deprecated for removal | Remover qualquer uso |

## 4. Text Blocks: fim da concatenação de SQL

> **Objetivo:** eliminar qualquer SQL escrito com `+` entre strings ou `StringBuilder.append()`. Em Java 17 não há justificativa para isso.

### 4.1 O problema que text block resolve

SQL escrito com concatenação tem três problemas ao mesmo tempo:

- **Ilegível:** o SQL real fica fragmentado entre aspas, espaços e operadores.
- **Frágil:** faltou um espaço antes ou depois da aspa e a query quebra silenciosamente.
- **Indepurável:** copiar o SQL do log e colar no banco exige limpeza manual.

```java
// ⚠️ Bug silencioso clássico: falta espaço antes de "FROM" e "WHERE"
String sql = "SELECT u.id, u.name, u.email" +
             "FROM users u" +
             "WHERE u.active = true";
// Resultado real: "SELECT u.id, u.name, u.emailFROM users uWHERE u.active = true"
```

Text blocks eliminam esse problema na raiz: a string é escrita **exatamente como o SQL deve ser lido**.

### 4.2 Sintaxe e regras essenciais

```java
String sql = """
    SELECT u.id, u.name, u.email
    FROM users u
    WHERE u.active = true
    """;
```

| Regra | Detalhe |
|---|---|
| Abertura: `"""` + quebra de linha | As três aspas de abertura **devem** ser seguidas de nova linha. Não pode haver texto na mesma linha. |
| Fechamento: posição das `"""` | Definem (junto com o conteúdo) o recuo base. O que estiver mais à direita é conteúdo. |
| Indentação automática | O Java remove o recuo comum de todas as linhas. O SQL gerado não tem espaços à esquerda. |
| *Trailing newline* | Se as `"""` de fechamento estão em linha própria, a string termina com `\n`. Para evitar, coloque `"""` no fim da última linha de conteúdo. |
| Escapes funcionam | `\n`, `\\`, `\"` seguem valendo. Use `\s` para forçar espaço no fim da linha. |
| `\` no fim da linha | Junta com a próxima linha (sem inserir `\n`). |

### 4.3 Exemplos progressivos de SQL

#### Query simples com parâmetros nomeados (Spring/JPA)

```java
// ❌ Antes
String sql = "SELECT o.id, o.status, o.total, o.created_at " +
             "FROM orders o " +
             "WHERE o.customer_id = :customerId " +
             "AND o.status IN (:statuses) " +
             "ORDER BY o.created_at DESC";

// ✅ Depois
String sql = """
    SELECT o.id, o.status, o.total, o.created_at
    FROM orders o
    WHERE o.customer_id = :customerId
    AND o.status IN (:statuses)
    ORDER BY o.created_at DESC
    """;
```

#### Query com JOIN e agregação

```java
// ❌ Antes — StringBuilder (comum em código de relatório legado)
StringBuilder sb = new StringBuilder();
sb.append("SELECT p.id, p.name, SUM(oi.quantity * oi.unit_price) AS revenue ");
sb.append("FROM products p ");
sb.append("JOIN order_items oi ON oi.product_id = p.id ");
sb.append("JOIN orders o ON o.id = oi.order_id ");
sb.append("WHERE o.created_at >= :startDate ");
sb.append("AND o.created_at < :endDate ");
sb.append("AND o.status = 'COMPLETED' ");
sb.append("GROUP BY p.id, p.name ");
sb.append("ORDER BY revenue DESC");
String sql = sb.toString();

// ✅ Depois — legível, copiável, depurável
String sql = """
    SELECT p.id, p.name, SUM(oi.quantity * oi.unit_price) AS revenue
    FROM products p
    JOIN order_items oi ON oi.product_id = p.id
    JOIN orders o ON o.id = oi.order_id
    WHERE o.created_at >= :startDate
    AND o.created_at < :endDate
    AND o.status = 'COMPLETED'
    GROUP BY p.id, p.name
    ORDER BY revenue DESC
    """;
```

#### Native query em repositório JPA

```java
@Query(value = """
    SELECT u.id, u.name, u.email, r.name AS role_name
    FROM users u
    JOIN user_roles ur ON ur.user_id = u.id
    JOIN roles r ON r.id = ur.role_id
    WHERE u.active = true
    AND (:roleId IS NULL OR r.id = :roleId)
    ORDER BY u.name
    """, nativeQuery = true)
List<UserProjection> findActiveByRole(@Param("roleId") Long roleId);
```

#### SQL dinâmico: quando text block não basta

Text block é para **SQL estático**. Se há cláusulas opcionais sendo concatenadas com `if/else`, use Criteria API, jOOQ ou uma query base com parâmetros opcionais.

```java
// ⚠️ Anti-pattern — voltou ao problema anterior, mesmo com text block
String sql = """
    SELECT * FROM users WHERE 1=1
    """;
if (filtroAtivo) sql += " AND active = true";
if (filtroRole != null) sql += " AND role = ?";

// ✅ Correto — parâmetros nullable na query base
String sql = """
    SELECT * FROM users
    WHERE (:active IS NULL OR active = :active)
    AND (:roleId IS NULL OR role_id = :roleId)
    """;
```

### 4.4 Text blocks além de SQL

O mesmo problema acontece com qualquer bloco de texto estático.

#### JSON para testes

```java
// ❌ Antes
String body = "{" +
    "\"name\": \"João\"," +
    "\"email\": \"joao@example.com\"," +
    "\"role\": \"ADMIN\"" +
"}";

// ✅ Depois
String body = """
    {
        "name": "João",
        "email": "joao@example.com",
        "role": "ADMIN"
    }
    """;
```

#### Mensagem de e-mail ou template

```java
// ✅ Combinado com formatted() (Java 15+)
String mensagem = """
    Olá, %s.
    Seu pedido #%d foi confirmado.
    Valor total: R$ %.2f
    Acesse o app para acompanhar a entrega.
    """.formatted(nomeCliente, numeroPedido, valorTotal);
```

### 4.5 Quando NÃO usar text blocks

| Situação | Por que não | O que usar |
|---|---|---|
| String de uma linha | Text block é mais verboso que aspas simples | String literal normal |
| SQL dinâmico com `if/else` | Volta ao problema de concatenação | Criteria API, jOOQ ou parâmetros opcionais |
| String que muda com frequência | O ganho está em ler algo estável | Externalizar para `.sql` ou `.properties` |
| Annotation que não aceita | Depende do compilador e da annotation | Testar antes (`@Query` do JPA aceita) |

## 5. Records: fim do DTO de 80 linhas

> **Objetivo:** toda classe que **só carrega dados**, sem lógica de negócio, deve ser avaliada como candidata a `record`.

### 5.1 O que records resolvem

Um DTO clássico tem **cinco elementos** que precisam ficar em sincronia:

1. Declaração dos campos
2. Construtor com todos os campos
3. Getters
4. `equals()` e `hashCode()` baseados em todos os campos
5. `toString()` legível

Qualquer mudança (adicionar, renomear, remover campo) exige atualizar os cinco. Com `record`, o compilador gera tudo e **mantém sincronizado por definição**.

### 5.2 Anatomia de um record

```java
public record ProductResponse(Long id, String name, BigDecimal price, boolean active) {}
//                            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
//                            componentes → campos + construtor canônico + acessores
//                                          + equals + hashCode + toString
```

| O que você escreve | O que o compilador gera |
|---|---|
| Componente `Long id` | Campo `private final Long id` |
| — | Acessor `id()` (**não** `getId()`) |
| — | Construtor canônico com todos os componentes |
| — | `equals()` e `hashCode()` baseados em todos os componentes |
| — | `toString()` legível: `ProductResponse[id=1, name=Caneta, ...]` |

### 5.3 Exemplos progressivos

#### DTO de resposta simples

```java
// ❌ Antes — 40+ linhas para 3 campos
public class UserResponse {
    private final Long id;
    private final String name;
    private final String email;

    public UserResponse(Long id, String name, String email) {
        this.id = id;
        this.name = name;
        this.email = email;
    }

    public Long getId()      { return id; }
    public String getName()  { return name; }
    public String getEmail() { return email; }

    @Override public boolean equals(Object o) { /* ... 10 linhas ... */ }
    @Override public int hashCode()            { /* ...  5 linhas ... */ }
    @Override public String toString()         { /* ...  5 linhas ... */ }
}

// ✅ Depois — 1 linha, comportamento idêntico
public record UserResponse(Long id, String name, String email) {}
```

#### DTO com Bean Validation

```java
// Annotations nos componentes funcionam normalmente
public record CreateUserRequest(
    @NotBlank String name,
    @Email @NotBlank String email,
    @NotNull @Size(min = 8) String password
) {}
```

#### Objeto de valor com validação (compact constructor)

```java
public record Email(String value) {
    public Email {  // compact: não redeclara os parâmetros
        if (value == null || !value.contains("@")) {
            throw new IllegalArgumentException("Email inválido: " + value);
        }
        value = value.strip().toLowerCase();  // normaliza antes de atribuir ao campo
    }
}

var email = new Email("  JOAO@EXAMPLE.COM  ");
// email.value() == "joao@example.com"
```

O *compact constructor* roda **antes** da atribuição aos campos: é o lugar certo para validar e normalizar.

#### Resposta paginada genérica

```java
public record PagedResponse<T>(
    List<T> content,
    int page,
    int totalPages,
    long totalElements
) {
    // Método factory — padrão comum com records
    public static <T> PagedResponse<T> of(Page<T> page) {
        return new PagedResponse<>(
            page.getContent(),
            page.getNumber(),
            page.getTotalPages(),
            page.getTotalElements()
        );
    }
}
```

#### Cuidado com a nomenclatura do acessor

```java
UserResponse user = new UserResponse(1L, "João", "joao@example.com");

user.id();     // ✅ correto
user.getId();  // ❌ não existe — erro de compilação
```

Jackson serializa records corretamente por padrão a partir da versão **2.12**:

```json
{ "id": 1, "name": "João", "email": "joao@example.com" }
```

Se o projeto usa Jackson mais antigo, atualize a dependência. Não é motivo para evitar records.

### 5.4 Onde records se encaixam

| Contexto | Record? | Motivo |
|---|---|---|
| DTO de request (Controller) | ✅ Sim | Imutável por natureza: o request não muda após o binding |
| DTO de response (Controller) | ✅ Sim | Só carrega dados para serialização |
| Projection do Spring Data | ✅ Sim | Pode substituir a interface de projection (ver 5.5) |
| Objeto de valor (*Value Object*) | ✅ Sim | Igualdade por valor é exatamente o que o record oferece |
| Entidade JPA (`@Entity`) | ❌ Não | Hibernate precisa de construtor sem args e mutabilidade (proxy, lazy loading) |
| Classe de domínio com lógica | ⚠️ Com cuidado | Pode ter métodos, mas se a lógica crescer, prefira classe normal |
| Classe com herança de implementação | ❌ Não | Records não podem estender classes (só implementar interfaces) |
| Objeto que precisa de setter | ❌ Não | Records são imutáveis |
| Lombok `@Data` / `@Value` em DTO | ✅ Substituir | Remove dependência de annotation processing desnecessária |

### 5.5 Record como projection (no lugar de interface de projection)

```java
// ❌ Antes — interface de projection (ainda funciona, mas verbosa)
public interface UserSummary {
    Long getId();
    String getName();
    String getEmail();
}

// ✅ Depois — record
public record UserSummary(Long id, String name, String email) {}

// No repositório (DTO projection por construtor)
List<UserSummary> findByActiveTrue();

// JPQL com construtor explícito sempre funciona
@Query("SELECT new com.exemplo.UserSummary(u.id, u.name, u.email) FROM User u WHERE u.active = true")
List<UserSummary> findActiveSummaries();
```

> Confirme a versão do Spring Data do projeto antes de depender da resolução automática. O JPQL com `new ...` funciona em qualquer versão.

### 5.6 Limitações reais de records

| Limitação | Impacto | Contorno |
|---|---|---|
| Todos os campos são `final` | Não muda campo após criar | Criar novo record com o valor atualizado (`withXxx()` manual se precisar) |
| Não herda de classe | Sem `extends` | Implementar interfaces; se precisa de herança, usar classe |
| Acessor sem `get` | Quebra código que chama `getId()` | Adaptar chamadores ou adicionar `getId() { return id(); }` |
| Frameworks antigos | MapStruct < 1.5, Jackson < 2.12 | Atualizar dependências |
| Não é `@Entity` | Não mapeia direto para tabela | Usar como DTO de saída; a entidade continua sendo classe normal |

## 6. Records e Text Blocks juntos

### 6.1 Repositório completo: antes e depois

```java
// ❌ Antes — repositório legado típico
public class OrderSummary {
    private Long orderId;
    private String customerName;
    private BigDecimal total;
    private String status;
    // construtor, getters, setters, equals, hashCode, toString...
}

@Repository
public class OrderRepository {
    private final JdbcTemplate jdbc;

    public List<OrderSummary> findByCustomer(Long customerId) {
        String sql = "SELECT o.id, c.name, o.total, o.status " +
                     "FROM orders o " +
                     "JOIN customers c ON c.id = o.customer_id " +
                     "WHERE o.customer_id = ? " +
                     "AND o.status <> 'CANCELLED' " +
                     "ORDER BY o.created_at DESC";
        return jdbc.query(sql, (rs, i) -> {
            OrderSummary s = new OrderSummary();
            s.setOrderId(rs.getLong("id"));
            s.setCustomerName(rs.getString("name"));
            s.setTotal(rs.getBigDecimal("total"));
            s.setStatus(rs.getString("status"));
            return s;
        }, customerId);
    }
}
```

```java
// ✅ Depois — record + text block
public record OrderSummary(Long orderId, String customerName, BigDecimal total, String status) {}

@Repository
public class OrderRepository {
    private final JdbcTemplate jdbc;

    private static final String FIND_BY_CUSTOMER = """
        SELECT o.id, c.name, o.total, o.status
        FROM orders o
        JOIN customers c ON c.id = o.customer_id
        WHERE o.customer_id = ?
        AND o.status <> 'CANCELLED'
        ORDER BY o.created_at DESC
        """;

    public List<OrderSummary> findByCustomer(Long customerId) {
        return jdbc.query(FIND_BY_CUSTOMER,
            (rs, i) -> new OrderSummary(
                rs.getLong("id"),
                rs.getString("name"),
                rs.getBigDecimal("total"),
                rs.getString("status")
            ),
            customerId
        );
    }
}
```

SQL como **constante de classe** tem um benefício extra: a query aparece no topo do arquivo, facilitando a revisão sem navegar pelo método.

> Repare que o `RowMapper` também ficou melhor: como o record é imutável, o construtor recebe tudo de uma vez, sem a sequência de `setXxx()` e sem objeto "meio preenchido".

### 6.2 Controller com record de request e response

```java
public record CreateOrderRequest(

public record OrderItemRequest(

```

## 7. Outras features de linguagem

### 7.1 `var` (Java 10)

Inferência de tipo **só para variáveis locais**. O tipo continua sendo estático, apenas não precisa ser escrito.

```java
// Antes
Map<String, List<Entrega>> porCidade = new HashMap<String, List<Entrega>>();

// Depois
var porCidade = new HashMap<String, List<Entrega>>();
```

| Use quando | Evite quando |
|---|---|
| O tipo já aparece no lado direito (`new ...`) | O tipo não é óbvio: `var result = process(data);` — qual tipo é `result`? |
| O tipo genérico é longo e repetitivo | Quando prejudica a leitura do código |

### 7.2 Pattern matching para `instanceof` (Java 16)

```java
// Antes
if (event instanceof OrderCreatedEvent) {
    OrderCreatedEvent created = (OrderCreatedEvent) event;
    process(created.getOrderId());
}

// Depois — o cast e a variável são feitos na própria condição
if (event instanceof OrderCreatedEvent created) {
    process(created.getOrderId());
}
```

### 7.3 `switch` expression (Java 14)

```java
// Antes
String label;
switch (status) {
    case PENDING: label = "Pendente"; break;
    case ACTIVE:  label = "Ativo";    break;
    case CLOSED:  label = "Fechado";  break;
    default: throw new IllegalArgumentException("Unknown: " + status);
}

// Depois
String label = switch (status) {
    case PENDING -> "Pendente";
    case ACTIVE  -> "Ativo";
    case CLOSED  -> "Fechado";
};  // o compilador garante exaustividade para enum
```

| Vantagem | Explicação |
|---|---|
| Sem *fall-through* | Cada `case ->` é isolado; não existe `break` esquecido |
| Retorna valor | Pode ser atribuído ou retornado direto |
| Exaustividade | Para enum, esquecer um caso é erro de compilação |

Para blocos com mais de uma linha por caso, use `yield`:

```java
int dias = switch (plano) {
    case MENSAL -> 30;
    case ANUAL -> {
        log.info("Plano anual");
        yield 365;
    }
};
```

### 7.4 Sealed classes (Java 17)

Restringem **quem pode estender** uma classe ou interface.

```java
public sealed interface Resultado permits Sucesso, Falha {}

public record Sucesso(String dados) implements Resultado {}
public record Falha(String erro)    implements Resultado {}
```

| Vale quando | Não vale quando |
|---|---|
| Hierarquia de domínio **fechada** (`Result`, tipos de pagamento) | Hierarquia pode crescer |
| Você quer o compilador verificando todos os casos | Usada por código externo ou plugins |

> Em Java 17, `switch` com pattern sobre sealed ainda é **preview**. A versão estável vem no Java 21.

## 8. Mudanças de API que valem a pena

### 8.1 Coleções imutáveis: `List.of`, `Set.of`, `Map.of`

```java
// Java 8
List<String> statuses = Collections.unmodifiableList(Arrays.asList("PENDING", "ACTIVE"));

// Java 17
List<String> statuses = List.of("PENDING", "ACTIVE");
```

| Cuidado | Detalhe |
|---|---|
| Não aceita `null` | `List.of(null)` lança `NullPointerException`. Se pode ter `null`, mantenha a forma antiga. |
| Imutável de verdade | `add`/`remove` lançam `UnsupportedOperationException` |
| Cópia imutável | `List.copyOf(outra)` (Java 10) |

### 8.2 `String`: `strip`, `isBlank`, `lines`, `repeat`

| Método | O que faz | Substitui |
|---|---|---|
| `strip()` | Remove espaços **Unicode** das pontas | `trim()` (só remove chars ≤ U+0020) |
| `isBlank()` | `true` se vazia **ou só com espaços** | `isEmpty()` quando espaços contam como vazio |
| `lines()` | `Stream<String>` com cada linha | `split("\n")` |
| `repeat(n)` | Repete a string `n` vezes | Laço com `StringBuilder` |
| `formatted(...)` | `String.format` como método de instância | `String.format(...)` |

### 8.3 `Optional` melhorado

```java
opt.ifPresentOrElse(
    v -> System.out.println("Achou: " + v),
    () -> System.out.println("Não achou")
);

Optional<String> resultado = opt.or(() -> Optional.of("padrão"));
String valor = opt.orElseThrow();   // sem argumento (Java 10)
```

| Use | Evite |
|---|---|
| Retorno de método que pode legitimamente não ter valor | Campo de classe |
| | Parâmetro de método |
| | Entidades (Hibernate não lida bem) |
| | Cadeias longas de `map().flatMap().filter().orElseGet()` |

### 8.4 Arquivos e HTTP

```java
// Java 8
String texto = new String(Files.readAllBytes(Paths.get("dados.txt")), StandardCharsets.UTF_8);

// Java 11
String texto = Files.readString(Path.of("dados.txt"));
Files.writeString(Path.of("saida.txt"), texto);
```

O `HttpClient` do Java 11 substitui o `HttpURLConnection` para chamadas HTTP simples, sem depender de biblioteca externa.

### 8.5 Streams

```java
// Java 9
Stream.of(1, 2, 3, 4, 1).takeWhile(n -> n < 4);   // 1, 2, 3
Stream.of(1, 2, 3, 4, 1).dropWhile(n -> n < 4);   // 4, 1

// Java 16
List<String> lista = stream.toList();   // imutável
```

### 8.6 `java.time` no lugar de `Date`/`Calendar`

```java
// ❌ Java 8 (legado ruim)
Date dataLimite = new Date();
Calendar cal = Calendar.getInstance();
cal.add(Calendar.DAY_OF_MONTH, 30);
dataLimite = cal.getTime();

// ✅ java.time (existe desde o Java 8, mas é frequentemente ignorado)
LocalDate dataLimite = LocalDate.now().plusDays(30);
```

Risco: converter `Date` legado para `LocalDate` exige atenção ao **fuso horário**.

## 9. O que muda na JVM e o que quebra na migração

### 9.1 Ganhos automáticos (zero esforço)

| Mudança | Efeito |
|---|---|
| G1GC como padrão | Menor latência de pausa out-of-the-box |
| NPE com detalhe | `Cannot invoke "String.length()" because "nome" is null` — diz qual variável |
| Melhorias de startup e footprint | Aplicação sobe mais rápido e usa menos memória |

### 9.2 O que pode quebrar

| Item | Problema | Ação |
|---|---|---|
| APIs removidas (`java.xml.ws`, CORBA, Nashorn, Applet) | Erro de compilação | Substituir por dependência externa (Jakarta EE) |
| `import sun.*` / `com.sun.*` | Acesso bloqueado | Remover ou migrar para API pública |
| Encapsulamento forte (`--illegal-access` removido) | Frameworks antigos falham por reflection | Atualizar o framework ou usar `--add-opens` como paliativo |
| Security Manager | Deprecated for removal | Remover qualquer uso |
| JPMS | Dependências legadas podem não funcionar como módulo | **Não** adotar JPMS em sistema com muitas dependências legadas |

> Rode a migração em duas etapas: **(1)** compilar e rodar tudo em 17 sem mudar código; **(2)** só depois adotar features novas.

## 10. O que vale a pena em código legado

### 🟢 Alto valor — aplicar sempre que encontrar

| Melhoria | Problema que resolve | Risco | Esforço |
|---|---|---|---|
| Records para DTOs | Boilerplate que esconde a intenção (DTO de 5 campos = 80 linhas) | Records são imutáveis: não substitui código que usa setter | Baixo |
| `List.of` / `Map.of` | Verbosidade e semântica obscura | Não aceita `null` | Baixíssimo |
| Text blocks para SQL e templates | SQL ilegível em concatenação | Zero (é só sintaxe) | Baixo |
| `strip()` no lugar de `trim()` | Comportamento errado com espaços não-ASCII | Zero | Trivial |
| NPE com detalhe | Debug lento | Nenhum | Nenhum |

### 🟡 Valor médio — aplicar com contexto

| Melhoria | Quando aplicar | Quando evitar |
|---|---|---|
| Pattern matching `instanceof` | Onde há `instanceof` seguido de cast | Lógica complexa |
| `switch` expression | `switch` em atribuição ou `return` | `switch` com lógica de negócio longa por caso |
| `var` | Tipo óbvio e longo no lado direito | Quando obscurece o tipo |

### 🔴 Apenas em casos específicos

| Melhoria | Vale quando | Não vale |
|---|---|---|
| Sealed classes | Hierarquia de domínio fechada | Hierarquia que cresce ou é usada externamente |
| `Optional` como retorno | O método pode legitimamente não retornar valor | Campo, parâmetro, entidade |

### ⚠️ Parecem boas, mas cuidado

- **Converter tudo para record:** entidades JPA, objetos com mutação controlada e validações complexas não são boas candidatas.
- **`Optional` em tudo:** não elimina `null`, é um *wrapper*. Encadear em lógica complexa piora a leitura.

## 11. Padrões de refatoração (antes e depois)

### 11.1 DTO verboso → Record

```java
// Java 8
public class UserResponse {
    private final Long id;
    private final String name;
    private final String email;
    public UserResponse(Long id, String name, String email) {
        this.id = id; this.name = name; this.email = email;
    }
    public Long getId() { return id; }
    public String getName() { return name; }
    public String getEmail() { return email; }
    // + equals, hashCode, toString...
}

// Java 17
public record UserResponse(Long id, String name, String email) {}
```

**Ganho:** elimina ~50 linhas, comunica imutabilidade, gera `equals/hashCode/toString` corretos.
**Não usar:** objetos mutados após criação, entidades JPA, POJOs com herança.

### 11.2 SQL em concatenação → Text block

```java
// Java 8
String sql = "SELECT u.id, u.name, u.email " +
             "FROM users u " +
             "WHERE u.active = true " +
             "AND u.created_at > :date";

// Java 17
String sql = """
    SELECT u.id, u.name, u.email
    FROM users u
    WHERE u.active = true
    AND u.created_at > :date
    """;
```

**Ganho:** legibilidade imediata, sem risco de esquecer espaço antes da aspa.
**Não usar:** string de uma linha.

### 11.3 `instanceof` com cast → Pattern matching

```java
// Java 8
void handle(DomainEvent event) {
    if (event instanceof OrderPlaced) {
        OrderPlaced placed = (OrderPlaced) event;
        orderService.process(placed.getOrderId());
    } else if (event instanceof OrderCancelled) {
        OrderCancelled cancelled = (OrderCancelled) event;
        orderService.cancel(cancelled.getOrderId(), cancelled.getReason());
    }
}

// Java 17
void handle(DomainEvent event) {
    if (event instanceof OrderPlaced placed) {
        orderService.process(placed.getOrderId());
    } else if (event instanceof OrderCancelled cancelled) {
        orderService.cancel(cancelled.getOrderId(), cancelled.getReason());
    }
}
```

**Ganho:** elimina o cast explícito e a chance de castar para o tipo errado após uma refatoração.

### 11.4 `switch` statement → `switch` expression

```java
// Java 8
public String describeStatus(OrderStatus status) {
    switch (status) {
        case PENDING:   return "Aguardando pagamento";
        case PAID:      return "Pago";
        case SHIPPED:   return "Enviado";
        case CANCELLED: return "Cancelado";
        default: throw new IllegalArgumentException(status.name());
    }
}

// Java 17
public String describeStatus(OrderStatus status) {
    return switch (status) {
        case PENDING   -> "Aguardando pagamento";
        case PAID      -> "Pago";
        case SHIPPED   -> "Enviado";
        case CANCELLED -> "Cancelado";
    };  // compilador valida a exaustividade do enum
}
```

> Se um novo valor for adicionado ao enum, esse `switch` **deixa de compilar** até ser tratado. No modelo antigo, o erro só aparecia em runtime, no `default`.

### 11.5 Coleção estática → `List.of`

```java
// Java 8
private static final List<String> VALID_STATUSES =
    Collections.unmodifiableList(Arrays.asList("PENDING", "ACTIVE", "CLOSED"));

// Java 17
private static final List<String> VALID_STATUSES = List.of("PENDING", "ACTIVE", "CLOSED");
```

### 11.6 `Date`/`Calendar` → `java.time`

Ver exemplo em [8.6](#86-javatime-no-lugar-de-datecalendar). Migre **ao tocar** o código, não em massa.

## 12. Guia de decisão rápida

### Quando substituir por text block

| Você vê no código | Substituir? |
|---|---|
| `String sql = "..." + "..." + "..."` | ✅ Sempre |
| `sb.append("..."); sb.append("...");` | ✅ Sempre |
| String com `\n` para quebra de linha | ✅ Se for bloco de texto fixo |
| JSON hardcoded em teste com `\"` escapado | ✅ Melhora muito a leitura |
| SQL com `if/else` concatenando partes | ❌ Resolver com parâmetros opcionais |
| String de uma palavra ou linha simples | ❌ Text block seria mais verboso |

### Quando substituir classe por record

| Você vê no código | Substituir? |
|---|---|
| Classe com só campos + construtor + getters | ✅ Candidata direta |
| Lombok `@Data` ou `@Value` sem lógica | ✅ Remove dependência |
| Interface de projection com getters | ✅ Record funciona igual |
| Classe com construtor público + campos `final` | ✅ Provavelmente já é um record manual |
| Classe com `@Entity` ou `@Table` | ❌ JPA não funciona com record |
| Classe com setters e mutação depois de criada | ❌ Records são imutáveis |
| Classe que estende outra classe | ❌ Records não permitem `extends` |
| Classe com lógica de negócio relevante | ⚠️ Avaliar; se crescer, prefira classe |

### Sistema de pontos para qualquer mudança

Para cada possível mudança, responda e some os pontos:

| Pergunta | Sim (+1) | Neutro (0) | Piora (−1) |
|---|---|---|---|
| Melhora a legibilidade? | Código fica mais claro | Neutro | Fica mais obscuro |
| Reduz boilerplate sem esconder lógica? | Menos linhas, mesma clareza | Neutro | Esconde lógica importante |
| Reduz risco de bug? | Ex.: exaustividade em `switch` | Neutro | Introduz semântica que confunde |
| É fácil de reverter? | Mudança superficial | Mudança estrutural | Difícil de desfazer |
| A equipe conhece o recurso? | Maioria conhece | Desconhecido | Ninguém conhece |
| Há testes cobrindo o comportamento? | Sim | Não | Não, e o código é crítico |

| Pontuação | Decisão |
|---|---|
| 4 a 6 | ✅ Fazer agora: ganho claro, baixo risco |
| 2 a 3 | ⚠️ Avaliar caso a caso: pesar equipe e criticidade |
| 0 a 1 | 🔴 Evitar por enquanto: custo/benefício desfavorável |
| Negativo | 🚫 Não fazer: piora a situação |

## 13. Checklist de revisão de código

Use ao revisar PRs. Cada item é uma **oportunidade**, não uma obrigação.

### Estrutura e boilerplate

- [ ] Classe só com campos, getters, `equals/hashCode/toString` e sem lógica? → candidata a **record**
- [ ] Construtor que apenas atribui campos? → reforça a candidatura a record
- [ ] Lombok `@Data`/`@Value` em DTO simples? → avaliar record

### Null e Optional

- [ ] `if (x == null)` onde o método poderia retornar `Optional`?
- [ ] `Optional` como campo ou parâmetro? → anti-pattern, remover
- [ ] `.get()` em `Optional` sem verificação? → bug latente; usar `orElseThrow()` ou `ifPresent()`

### Strings

- [ ] `trim()`? → trocar por `strip()`
- [ ] Concatenação com `\n` ou `+` no fim de cada linha? → **text block**
- [ ] `isEmpty()` onde `isBlank()` seria mais correto?

### Coleções

- [ ] `Arrays.asList()` + `Collections.unmodifiableList()`? → `List.of()`
- [ ] `new HashMap<>()` + `put()` + `unmodifiableMap()`? → `Map.of()` ou `Map.copyOf()`
- [ ] `List.of()` recebendo `null`? → bug, `List.of` não aceita `null`

### `switch` e condicionais

- [ ] `switch` com `break` e atribuição? → `switch` expression
- [ ] `switch` em enum sem tratar todos os casos? → expression força exaustividade
- [ ] `if/else if` em cadeia mapeando enum/tipo para valor? → `switch` expression

### Pattern matching

- [ ] `instanceof` seguido de cast para a mesma variável? → pattern matching
- [ ] Sequência de `if instanceof` para tipos diferentes? → candidata a `switch` com pattern (Java 21+)

### APIs e imports

- [ ] `Date`, `Calendar`, `SimpleDateFormat`? → `java.time` ao tocar
- [ ] `StringBuffer` onde `StringBuilder` bastaria?
- [ ] `import com.sun.*` ou `sun.*`? → remover (bloqueado em 17)
- [ ] Dependência de APIs removidas (`javax.xml.ws`, Nashorn)? → substituir antes de subir

|---|---|---|---|---|

## 15. Armadilhas e boas práticas

### O que realmente melhora

- Records eliminam um tipo inteiro de bug: `equals/hashCode` inconsistente em POJOs.
- Text blocks eliminam erros silenciosos de SQL mal formatado.
- `switch` expression elimina *fall-through* e força exaustividade em enums.
- NPE detalhado reduz o tempo de debug sem esforço.
- `strip()` corrige silenciosamente o comportamento incorreto de `trim()`.
- G1GC como padrão melhora a latência sem nenhuma mudança.

### O que é só estilo

- `var` em variáveis simples: ganho marginal se o tipo já é óbvio, zero se obscurece.
- `Optional` em todo retorno nullable: não é melhoria automática, é *trade-off*.
- Encadear `Optional` com `map/flatMap` em lógica simples: piora a leitura.

### O que pode piorar a legibilidade

- `var result = process(data);`: qual tipo é `result`?
- `switch` expression com `yield` e várias linhas por caso: perde a clareza que justificava a expression.
- `Optional.map().flatMap().filter().orElseGet()` em cadeia longa: dificulta o debug.
- Record com *compact constructor* cheio de validação: pode ser melhor uma classe com construtor explícito.

### Armadilhas comuns

| Armadilha | Explicação | Solução |
|---|---|---|
| Esquecer o espaço na concatenação de SQL | Query quebra sem aviso | Text block |
| Chamar `getId()` em record | Não existe, é `id()` | Usar `id()` ou adicionar método |
| `List.of(...)` com `null` | `NullPointerException` | `Arrays.asList` ou remover o `null` |
| Modificar `List.of(...)` / `stream.toList()` | `UnsupportedOperationException` | `new ArrayList<>(...)` |
| Record como `@Entity` | Hibernate exige construtor sem args e mutabilidade | Classe normal para a entidade |
| Text block com `if/else` colando SQL | Volta ao problema original | Parâmetros opcionais na query |
| `"""` com texto na mesma linha | Erro de compilação | Quebrar linha após a abertura |
| Trailing newline inesperado | `"""` em linha própria adiciona `\n` | Fechar na última linha de conteúdo |
| Sealed em hierarquia pública | Extensão externa deixa de ser possível | Só usar em domínio fechado |
| Migrar e refatorar juntos | Impossível saber o que causou a falha | Migrar primeiro, refatorar depois |

### O que evitar em legado sensível

- Não converta **entidades JPA** para records.
- Não use **sealed classes** em hierarquias que parceiros ou plugins estendem.
- Não substitua frameworks que usam `sun.*` sem validar em Java 17 com `--add-opens`.
- Não adote **JPMS** em sistemas com muitas dependências legadas: custo altíssimo, benefício discutível.

### Como introduzir mudanças de forma incremental

1. Comece pelos **records**: baixo risco, alto ganho, fácil de revisar.
2. Aplique **text blocks** na próxima vez que tocar um SQL hardcoded.
3. Aplique `strip()` em qualquer PR que já mexa em strings.
4. Introduza `switch` expression quando já estiver refatorando a lógica; sozinho não é prioridade.
5. Migre `Date/Calendar` para `java.time` **ao tocar** o código, não em massa.
6. Use o checklist da seção 13 no template de PR: como oportunidade, não como obrigação.

## 16. Cheat sheet

### Do antigo para o novo

| Java 8 | Java 17 |
|---|---|
| `"a" + "b" + "c"` em SQL | `""" ... """` |
| Classe DTO com getters/equals/hashCode | `record Nome(Tipo campo) {}` |
| `Collections.unmodifiableList(Arrays.asList(...))` | `List.of(...)` |
| `if (x instanceof Foo) { Foo f = (Foo) x; }` | `if (x instanceof Foo f)` |
| `switch` com `break` | `switch` com `->` |
| `trim()` | `strip()` |
| `s.isEmpty()` (com espaços) | `s.isBlank()` |
| `new ArrayList<String>()` na variável | `var lista = new ArrayList<String>()` |
| `Date` / `Calendar` | `LocalDate` / `LocalDateTime` / `ZonedDateTime` |
| `new String(Files.readAllBytes(...))` | `Files.readString(...)` |
| `stream.collect(Collectors.toList())` | `stream.toList()` (imutável) |
| `String.format("...", a)` | `"...".formatted(a)` |

### Record em 30 segundos

```java
public record Entrega(String cliente, String cidade, double frete) {

    public Entrega {                       // compact constructor: valida/normaliza
        if (frete < 0) throw new IllegalArgumentException("Frete negativo");
    }

    public boolean gratis() {              // métodos são permitidos
        return frete == 0;
    }

    public static Entrega gratuita(String cliente, String cidade) {  // factory
        return new Entrega(cliente, cidade, 0);
    }
}

var e = new Entrega("Mercado Sol", "Taubaté", 450.0);
e.cliente();    // acessor sem "get"
e.toString();   // Entrega[cliente=Mercado Sol, cidade=Taubaté, frete=450.0]
```

### Text block em 30 segundos

```java
String sql = """
    SELECT *
    FROM entrega
    WHERE cidade = ?
    """;               // fechamento em linha própria → termina com \n
```

### Decisão em uma frase

> Só dados, sem mutação, sem herança → **record**. Texto fixo em várias linhas → **text block**. Tipo óbvio e longo → **`var`**. Lógica de negócio por caso → **não force `switch` expression**. Entidade JPA → **classe normal**.
